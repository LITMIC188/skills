# Web-Design

## 1. 定义、文件与注册

组合五个依赖完成网页、网站及工作台布局设计，再优化 React / Next.js 页面性能，最后测试并交付可复现结果。用户指定的技能名称、外部注册名称及 UI 名称均为 `Web-Design`；Codex 原生 frontmatter 与目录使用小写技术标识 `web-design`，两者指向同一技能。此映射适配本机原生校验器，不改变下面四字段的 name。

这是编排技能，不是安装器。读取会话技能目录中实际可用的依赖 SKILL.md 后才执行其流程；缺失时执行第 4 节具体回退。不得臆造调用接口、宣称缺失依赖已运行，或自动安装来源不明的同名技能。实现沿用用户项目的框架、组件及版本约束，不扩大到用户未要求的发布或外部写入。

```text
web-design/
  SKILL.md                         完整规则、五个依赖、三个阶段和验收
  agents/openai.yaml               Codex UI 名称与自动发现策略
  references/registration.json     外部注册的四个固定字段，顺序不变
  references/registration-fields.md 字段名、类型、示例值和匹配契约
  scripts/match_trigger.py         确定性判定器，标准库即可运行
  scripts/test_match_trigger.py    正负边界的可执行验证
```

注册时读取 [字段说明](references/registration-fields.md) 和 [四字段 JSON](references/registration.json)。`triggers` / `match_description` 是外部匹配字段，不放入不支持它们的 Codex frontmatter 顶层。description 用于发现候选，执行前必须通过字面判定器。宿主自动发现不等于支持确定性预匹配；外部注册器须接入判定器。本技能不声称只写描述即可改变宿主路由算法。

## 2. 触发边界判定规则（用户要求全文）

### 1. 大小写与空白归一化规则：

- 所有触发词匹配前，统一将用户输入与触发词做 Unicode NFKC 归一化、去除首尾空白、将连续空白压缩为单个空格
- 英文触发词匹配时忽略大小写；中文触发词不做大小写处理但需完全一致匹配
- 示例：`Skills<Web-Design>`、`skills<web-design>`、`SKILLS<WEB-DESIGN>` 均判定为命中 `skills<Web-Design>`

### 2. 触发词分层规则：

- 核心触发词（命中任一即直接触发，无需额外条件）：
  - `设计网页`
  - `设计网站`
  - `设计工作台布局`
  - `skills<Web-Design>`
- 扩展触发词（命中后需与上下文中的“网页/网站/工作台布局/React/Next.js/webapp”任一领域词共同出现，方可触发）：
  - `优化 React 页面性能`
  - `优化 Next.js 页面性能`
  - `测试 webapp`
- 扩展触发词单独出现且无领域词共现时，判定为不触发，并在 SKILL.md 中记录该边界判定说明

### 3. 显式调用优先规则：

- 当用户输入包含 `skills<Web-Design>`（含大小写与空白归一化后的等价形式）时，跳过扩展触发词共现校验，直接触发

### 4. 失败回退合格标准：

- 任一依赖 skill 调用失败时，回退结果必须同时满足以下全部条件，方视为“合格回退”：
  a. 明确指出失败的依赖 skill 名称与失败原因
  b. 给出已完成的可用产出物或可继续执行的替代步骤
  c. 不阻塞后续阶段：若失败发生在设计与布局阶段，须给出可继续性能优化与测试的最小可用产出；若失败发生在性能优化阶段，须保留设计产出并继续测试阶段；若失败发生在测试阶段，须输出已完成的测试范围与未覆盖范围
  d. 回退说明必须可被下一步直接读取执行，不得仅给出笼统提示
- 未同时满足 a–d 的回退，判定为“不合格回退”，须在 SKILL.md 中标注为需重试或人工介入

## 3. 可执行判定补充与边界

为满足“单独出现 `优化 React 页面性能` 不触发”的指定示例，**上下文共现**指触发短语之外另有领域词；短语自身含有的 React / Next.js / webapp 不计入。先遮蔽输入中所有扩展触发短语，再在剩余文本查领域词，避免两个扩展短语互相提供自身领域词。领域词可在同一条用户消息任意位置；不读取历史消息、代理输出或工具结果充当共现证据。

只作字面包含匹配，不作近义词、意图、否定句或引述推断；触发只决定选择技能，具体工作仍遵循用户实际指令。中文短语必须连续完全相同，不将 `设计 网页` 合并为 `设计网页`。NFKC / 空白压缩不删除内部空格，因此 `skills< Web-Design >` 不等同于 `skills<Web-Design>`。

英文大小写仅折叠 ASCII A–Z，混合短语的中文不变。英文领域词须有非 ASCII 字母、数字、下划线边界；`React组件` 可命中 React，`ReactNative`、`webapplication` 不算 React / webapp。中文领域词按连续字面匹配。固定顺序：显式调用 → 其他核心词 → 扩展词及额外领域词 → 不触发。

输入与词表共用 normalize()，JSON 前四项为核心、后三项为扩展；位置不可更改。运行：

```sh
python scripts/match_trigger.py --text "  Skills<Web-Design>  "
python scripts/match_trigger.py --text "React 项目：优化 React 页面性能"
python scripts/test_match_trigger.py
```

判定器输出 JSON：matched（布尔）、reason（explicit/core/extended_with_domain/extended_without_domain/no_trigger）、归一化输入、命中词、剩余上下文领域词。未命中也是正常结果，退出码为 0；执行错误返回非零。没有 Python 时照同一算法判定并保存证据，不能改为模糊匹配。

外部注册器也可调用 `python scripts/match_trigger.py --stdin`，将当前消息以 UTF-8 编码写入标准输入。标准输入和输出均使用 UTF-8，不依赖 Python UTF-8 模式是否开启；非法 UTF-8 输入属于执行错误，不能当作匹配结果。

| 输入 | 判定 | 原因 |
| --- | --- | --- |
| `  Skills<Web-Design>  ` | 触发 | 去首尾空白、英文忽略大小写，显式调用优先 |
| `ＳＫＩＬＬＳ＜ＷＥＢ－ＤＥＳＩＧＮ＞` | 触发 | NFKC 后等同显式调用 |
| `React 项目：优化\tReact  页面性能`（\t 表示制表符） | 触发 | 空白压缩后命中扩展词，短语之外有 React |
| `优化 React 页面性能` | 不触发 | 自带 React 不算上下文共现 |
| `优化 React 页面性能；测试 webapp` | 不触发 | 所有扩展短语之外无领域词 |
| `网站：测试 WEBAPP` | 触发 | 扩展词忽略英文大小写，另有网站 |
| `skills< Web-Design >` | 不触发 | 内部空白不会删除 |
| `做个网页` / `设计 网页` | 不触发 | 无任一完整触发短语 |

## 4. 五个依赖 skill 使用规则

### 4.1 调用顺序、共同输入与回退记录

默认设计入口按 `UI Ux Pro Max → Frontend Design → shadcn → react-best-practices → webapp-testing` 顺序执行。前项输出或合格回退作为后一项输入。先在会话技能目录解析真实文件并读其说明，再由当前代理执行其中的操作；名称别名只有在实际元数据或文档可核验时才采用。不把这些名称当作现成函数。

核心设计词入口执行三个阶段。仅性能扩展词命中且已有设计/代码时，设计阶段记录“沿用”，按需补布局或组件后优化及测试。仅测试扩展词命中时，盘点已有设计与性能证据后测试；只有测试发现的相关缺陷才返回相应依赖修复。显式调用按用户请求选入口；未给目标时先读项目，只询问影响实施的缺失信息。不为执行五个依赖重做无关设计或改写非 React 项目。

在用户项目内约定产出目录（默认 `artifacts/web-design/`，已有规范优先）：brief.md、design.md、implementation.md、performance.md、testing.md，以及按需生成的 fallback.json。这些是执行时产物，不是技能包空白占位文件。

每次失败向 fallback.json 数组追加以下结构，填写真实路径、步骤与原因：

```json
{
  "dependency": "shadcn",
  "stage": "design",
  "reason": "当前会话技能目录未提供 shadcn",
  "artifacts": ["src/components/Button.tsx", "artifacts/web-design/implementation.md"],
  "alternative_steps": ["在项目根目录执行 package.json 中已核验的 dev 脚本"],
  "next_stage": "performance",
  "handoff": {"project_root": ".", "entry_files": ["src/components/Button.tsx"], "command_source": "package.json"},
  "checks": {"a": true, "b": true, "c": true, "d": true},
  "status": "qualified",
  "uncovered": ["未使用 shadcn skill 生成组件"],
  "retry_or_intervention": null
}
```

这是格式示例，不能将不存在的按钮或未经核验的脚本写成已完成产物。a 核对依赖名称及具体原因；b 核对产出可用或步骤可执行；c 核对下阶段所需输入真实存在并可继续；d 核对目录、入口、命令、约束及未覆盖项能被直接读取执行。逐项核验后才填 true。

**五个依赖统一的不合格回退处理**：任一项为 false，status 写 `unqualified_retry_or_intervention`，指出缺项及修复步骤。原因可修复时最多针对该原因重试一次；仍不合格则报告人工介入所需具体资料/权限/运行条件，保留可用产物并继续独立步骤。不得宣称整条流程完成；后续能执行不等于前阶段通过。

### 4.2 UI Ux Pro Max：需求和设计系统

- **调用触发条件**：需要新设计页面/网站/工作台，或现有设计缺少本次布局和视觉约束。
- **前置依赖**：触发通过；用户需求、项目位置和已有素材。非关键偏好可作可修订假设，技术目标缺失时询问并继续盘点。
- **输入**：brief.md、页面清单、用户任务、内容结构、框架/品牌/屏幕约束、现有截图和组件系统（仅已有资料）。
- **输出**：design.md 的导航、信息层级、工作台区域、响应式断点、颜色/字体/间距 token、交互状态、可访问性约束。
- **衔接方式**：Frontend Design 将 design.md 实现为页面；shadcn 复用 token。
- **失败回退 a**：记录 `UI Ux Pro Max` 不可用/文件不可读/操作失败和具体原因。
- **失败回退 b**：从用户品牌及既有样式提取 token；无既有系统时写出最小导航、内容区、间距、颜色、断点、状态，并以项目框架实现入口页。
- **失败回退 c**：交付真实最小入口页及样式/状态，支持继续组件实现、性能优化与测试；仅理念或未实现线框不合格。
- **失败回退 d**：design.md 给出 token 实值和区域/状态约束，implementation.md 给出入口文件、启动命令、检查路径；fallback.json 引用产物并逐项判定 a–d。不合格依 4.1 重试或人工介入。

### 4.3 Frontend Design：设计实现与布局

- **调用触发条件**：design.md 确定需实现/修改的页面，或已有页面不满足本次布局要求。
- **前置依赖**：UI Ux Pro Max 输出或合格回退；沿用设计时须有 token 与区域约束。
- **输入**：brief.md、design.md、真实路由/源码、构建配置、数据契约及交互需求。
- **输出**：可运行页面、响应式布局、组件骨架、必需加载/空/错误状态；implementation.md 的文件、入口、命令和操作路径。
- **衔接方式**：shadcn 接收骨架与组件清单；性能阶段接收实际 React/Next.js 源码；测试阶段接收可操作页面。
- **失败回退 a**：记录 `Frontend Design` 与原因，区分依赖缺失、生成失败和项目无法启动。
- **失败回退 b**：用现有组件实现最小语义布局（导航/内容区及所需工作台栏）、至少一条核心操作及必需状态；新项目使用用户选定框架。
- **失败回退 c**：保存真实源码与可运行入口，支持性能分析及测试；运行环境缺失时可继续静态检查，但未证实可运行的设计回退不能判为合格。
- **失败回退 d**：implementation.md 记录文件、路由、安装条件、核验过的命令、核心操作/状态；fallback.json 逐项判 a–d。不合格依 4.1 处理并继续不依赖该环境的独立检查。

### 4.4 shadcn：组件落地和统一

- **调用触发条件**：页面需按钮、表单、对话框、表格、侧栏等组件，且项目允许使用或已用 shadcn。
- **前置依赖**：Frontend Design 骨架或合格回退及 token；框架不支持该体系则记录不适用，不强行迁移。
- **输入**：组件清单、状态、token、已有组件目录、项目配置、允许的依赖版本。
- **输出**：真实组件及页面接线、统一样式、键盘/焦点/标签与禁用/错误状态；implementation.md 组件映射。
- **衔接方式**：最终集成页面交给 react-best-practices，不停在独立示例；交互/键盘路径交给 webapp-testing。
- **失败回退 a**：记录 `shadcn` 失败及原因，不以“类似组件”掩盖失败。
- **失败回退 b**：复用已有可访问组件，否则以语义化原生按钮/输入/表格实现交互；复杂控件无法等价实现时降为可用简单交互并记录差异。
- **失败回退 c**：入口保持可运行、核心操作可用，继续优化/测试；替换失败导入，不遗留破坏构建的引用。
- **失败回退 d**：组件映射给出替换文件、行为差异、限制、后续命令/测试路径；fallback.json 逐项判 a–d。不合格依 4.1 重试或人工介入。

### 4.5 react-best-practices：React / Next.js 性能

- **调用触发条件**：涉及 React/Next.js 源码且设计可用，或性能扩展入口带入已有页面；非 React 项目记录不适用后进入测试。
- **前置依赖**：可用设计实现/沿用代码及构建配置；shadcn 已完成、合格回退或不适用。不得为指标破坏核心行为。
- **输入**：源文件、构建脚本、依赖清单、运行环境、核心路径、可获得的性能基线。
- **输出**：针对实际问题的修改及 performance.md，含请求/渲染/客户端包/资源加载问题、改动理由、前后证据及未测项。不盲目加 memo 或无依据声称提速。
- **衔接方式**：webapp-testing 验证最终代码，重点覆盖优化影响的数据、加载及操作路径；保留设计约束和指标口径。
- **失败回退 a**：记录 `react-best-practices` 失败及具体原因。
- **失败回退 b**：保留设计源码，直接检查实际串行请求、重复渲染、过量客户端代码和资源加载，只改有依据且能核验的项；无可改问题时报告检查范围，不虚构修改。
- **失败回退 c**：证据不足不作改善声明；保留设计，撤回本阶段导致损坏的局部修改，继续测试可用版本。
- **失败回退 d**：performance.md 写检查文件、已改/未改、环境、命令、基线缺失及需复测路径；fallback.json 指明交给测试的代码版本并判 a–d。不合格依 4.1 处理。

### 4.6 webapp-testing：最终验证

- **调用触发条件**：设计/性能阶段有可用页面，或测试扩展入口带入已有 webapp。纯设计稿无可执行页面时记录限制并检查可检查内容，不冒称端到端通过。
- **前置依赖**：implementation.md、最终代码、performance.md 或不适用/回退状态、已核验启动方式与入口。
- **输入**：页面/核心路径/预期、视口、可用浏览器能力、地址、性能改动点、状态和键盘检查清单。
- **输出**：testing.md，记录真实命令/工具/环境、通过/失败/未执行、截图/日志、复现步骤及未覆盖范围。
- **衔接方式**：可修复缺陷回到相应设计/组件/性能阶段，修复后重测受影响路径；最终交付证据并区分实现完成与验证不足。
- **失败回退 a**：记录 `webapp-testing` 缺失/失败及原因，例如浏览器工具不可用或服务无法启动。
- **失败回退 b**：执行项目已有相关测试、构建、静态检查，或用可用浏览器工具操作同一核心路径；只记真实完成范围。
- **失败回退 c**：浏览器不能运行时仍输出已完成范围（可为零，但须解释）与未覆盖范围，保留设计/性能产物。
- **失败回退 d**：testing.md 给逐项结果、日志、复现命令、环境、待测输入/步骤/预期；fallback.json 判 a–d。无可执行替代步骤或缺少范围记录则不合格，依 4.1 重试或人工介入，不标“全通过”。

## 5. 从触发到交付的使用流程

### 阶段 0：触发、范围与现有产出盘点

- **输入**：本条用户消息及四字段 JSON；项目/历史资料仅用于实施，不用于触发共现。
- **操作步骤**：按第 2 节全文规则与第 3 节补充运行判定器；未命中不执行本技能。命中后将证据写入 brief.md；识别设计/优化/测试入口，读取项目约束和实际依赖 SKILL.md。只要设计稿时按授权产物工作，明确代码阶段的范围限制，不自行扩大任务。
- **阶段产出物**：brief.md 及判定器的完整 JSON 输出，含命中类型、需求/范围、已有设计/源码、框架、依赖可用性、入口、必要假设和验收需求。Python 可用时必须实际执行判定器并保存原始 JSON，领域词证据使用 context_domains 的真实值，不能凭文字解释替代执行结果。
- **验收检查点**：只依字面规则；`  Skills<Web-Design>  ` 触发，单独 `优化 React 页面性能` 且无额外领域词不触发；引用规则与判定 JSON 一致。

### 阶段 1：设计与布局

- **输入**：brief.md、项目、素材及已有设计。
- **操作步骤**：① UI Ux Pro Max 定结构/token；② Frontend Design 实现响应式页面骨架/状态；③ shadcn 集成组件并检查导入/操作路径；失败按 4.2–4.4 回退。性能/测试入口可沿用已有设计并记录位置。
- **阶段产出物**：design.md、真实页面/组件/样式、implementation.md；按需 fallback.json。最小实现含可运行入口、主布局、至少一条核心操作、需求必需的加载/空/错误状态、下阶段可用源码和启动命令。
- **验收检查点**：结构符合需求；检查项目目标视口，未给尺寸时以 375/768/1440 像素为可修订默认值；可执行时确认无横向溢出、标签/键盘/焦点可用，核验构建或启动并留证。不将未执行检查写成通过，不扩大功能范围。

### 阶段 2：性能优化

- **输入**：最终设计源码、配置、implementation.md、已有基线。
- **操作步骤**：① 判 React/Next.js 适用性；② 依 4.5 读取 react-best-practices 查实际瓶颈；③ 对相关问题最小修改；④ 同页面/环境/口径复测可测项；失败保留设计继续测试。测试入口只盘点现有性能证据，有相关缺陷才优化。
- **阶段产出物**：可用最终代码及 performance.md，包括基线/改后证据、理由、未测项；非 React 或不在范围内的优化记录不适用/沿用状态。
- **验收检查点**：未破坏设计或行为；修改有问题依据；指标有来源和前后条件；基线缺失只报告检查/修改，不声称已证实提速。

### 阶段 3：测试

- **输入**：最终代码/页面、implementation.md、performance.md、核心路径及回退记录。
- **操作步骤**：① 按 4.6 启动或接入页面；② 用 webapp-testing 验核心路径、受影响布局/视口、必需状态、键盘和控制台错误；③ 执行适用构建/类型检查/已有相关测试；④ 修复本次缺陷，重测受影响项；失败执行具体替代检查。
- **阶段产出物**：testing.md、实际截图/日志/报告；按需更新代码、performance.md 与 fallback.json。
- **验收检查点**：结论有证据，失败与未执行分开；交互/性能修改有回归检查；动态列表用键盘切换状态后核验焦点仍在原控件，原控件因筛选消失时转移到合理可操作项，不仅检查标签/状态就判键盘通过；浏览器不可用明确待测视口/路径/状态/步骤；逐项核验所有回退 a–d，验证不足不等于通过。

### 阶段 4：最终交付

- **输入**：设计、实现、性能、测试产物及失败/未执行列表。
- **操作步骤**：核对真实文件、可读命令和项目配置，给出产物位置、完成行为、验证证据、限制及下一步。不把缺失依赖、静态检查、未测指标写成调用完成。
- **阶段产出物**：可用页面/设计和阶段记录链接、状态、可直接执行的下一步；无发布需求不发布。
- **验收检查点**：覆盖本次授权范围；五个依赖都有执行/沿用/不适用/失败回退状态；回退按 a–d 核验；不合格项标“需重试或人工介入”。

## 6. 技能包验收

1. 第 2 节完整保留触发边界规则；第 3 节明确独立扩展词与空白边界。
2. 注册字段依次为 name、description、triggers、match_description；逐个列字段名/类型/示例值；triggers 为 JSON string[]；分层、共现及显式优先可执行。
3. 第 4 节覆盖五个依赖的条件、前置、输入、输出、衔接、分别满足 a–d 的失败回退及不合格处理。
4. 第 5 节每阶段具备输入、操作、产出与验收，可沿用已有设计进入优化/测试。
5. 运行脚本边界测试与 skill-creator quick_validate.py；分别验证匹配行为及原生结构，不代表五个依赖已运行或实际项目测试已完成。
